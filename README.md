# EzyStocks 재고조사

의류 브랜드 재고 실사용 Android 앱. 재고조사 핵심 기능은 완전 오프라인으로 동작하며,
공식몰 상품정보 보강과 EZYSTOCK_SYNC 연결만 사용자가 실행할 때 네트워크를 쓴다.

현재 홈은 `재고 실사`, `일부 실사`, `입고 물류 조사`의 세 작업으로 구분한다.
최초 데이터가 없는 기기에서는 브랜드를 먼저 선택하며, 선택한 브랜드는 이후 파일 가져오기의
기본값으로 사용된다. 완료·진행 중인 작업은 `작업 내역`의 `실사 내역`과 `입고 내역` 탭에
각각 보존된다. 완료된 실사는 결과 화면으로, 진행 중인 실사와 입고 조사는 작업 화면으로 다시 연다.
입고 물류 조사는 상품을 먼저 하나 고르는 방식이 아니라 날짜·시간 이름의 새 박스를 만든 뒤,
그 박스에서 여러 품번의 바코드를 연속으로 찍는 방식이다. 스캔된 SKU는 박스에 자동 추가되며
박스 이름은 사용자가 수정할 수 있다.
카탈로그에 없는 바코드는 브랜드의 기존 학습 규칙으로 품번·컬러·사이즈를 제안하며,
사용자가 확인하면 신규 상품정보로 영구 저장하고 해당 박스에 즉시 1개 반영한다.
일부 실사는 검색 결과에서 같은 브랜드의 여러 상품을 선택해 하나의 조사로 시작할 수 있다.
또한 시작 화면에서 `파일 업로드로 시작`과 `파일 없이 시작`을 선택할 수 있으며,
파일로 만든 일부 실사도 전체 실사와 별도 유형으로 기록된다. 작업 내역에서는 전체·일부 실사
표시와 검색, 진행 상태 필터를 제공하며 실사·입고 내역을 확인 후 개별 삭제할 수 있다.
입고 박스는 CSV와 Excel로 내보낼 수 있으며 Excel에는 상세·요약 시트가 함께 생성된다.
PC와 WebSocket으로 연결된 동안 실사·입고 수량 변경은 절대수량 이벤트로 실시간 전송된다.
전송 규격은 `docs/SYNC_PROTOCOL.md`에 고정한다.

## 빌드하기

`build-apk.bat` 을 더블클릭하면 끝난다. JDK / Android SDK / Gradle 을 알아서 찾고,
Gradle 이 없으면 받아서 쓰고, 완성된 APK 를 `output\` 폴더에 날짜를 붙여 넣어준다.

**PowerShell 에서 실행할 때는 반드시 앞에 `.\` 를 붙인다.**
PowerShell 은 보안상 현재 폴더의 명령을 그냥 실행하지 않는다.

| 명령 | 하는 일 |
|---|---|
| `.\build-apk.bat` | 디버그 APK 빌드 (기본) |
| `.\build-apk.bat install` | 빌드 후 USB 로 연결된 폰에 바로 설치 |
| `.\build-apk.bat release` | 릴리스 APK 빌드 (난독화 + 용량 축소). **`keystore.properties` 가 있어야 돈다** |
| `.\build-apk.bat test` | 유닛 테스트만 실행 |
| `.\build-apk.bat clean` | 빌드 캐시 정리 |

> **폰에 설치할 거면 디버그 APK 를 쓸 것.** 파일 이름에 `-debug-` 가 들어간 쪽이다.
>
> 안드로이드는 **서명 없는 APK 를 거부**하고 **"패키지가 잘못되어 앱이 설치되지 않았습니다"** 만 띄운다.
> APK 가 깨진 것이 아니라 원래 설치가 안 되는 물건이다.
> (실제로 한 번 겪었다. `output/` 을 정리하다 디버그 APK 를 다 지우고
>  서명 없는 릴리스 APK 만 남아서 그것을 설치하려다 벌어진 일이다)
>
> 그래서 **`keystore.properties` 가 없으면 릴리스 빌드는 아예 시작하지 않는다.**
> 난독화 빌드는 몇 분씩 걸리는데, 그 끝에 나오는 것이 설치도 못 하는 파일이면 시간만 버린다.
> 스크립트가 1초 만에 멈추고 무엇을 해야 하는지 알려준다.
>
> `keystore.properties` 는 있는데 `storeFile` 경로가 실제로 없으면 Gradle 이 서명 없이 빌드한다.
> 그 경우에는 APK 경로 바로 옆에 경고가 붙는다.
>
> 지금 갖고 있는 APK 가 설치되는 물건인지 확인하려면:
>
> ```
> %LOCALAPPDATA%\Android\Sdk\build-tools\34.0.0\apksigner.bat verify 파일.apk
> ```
>
> `Verifies` 가 나오면 설치된다. `DOES NOT VERIFY` / `Missing META-INF/MANIFEST.MF` 면 서명이 없는 것이다.

### 이 PC 에서 실제로 겪은 문제들 (배치 파일이 자동으로 처리한다)

빌드를 처음 돌리면서 환경 문제 다섯 가지를 찾아 해결했다. 다른 PC 로 옮길 때 참고할 것.

| 문제 | 증상 | 대응 |
|---|---|---|
| `%TEMP%` 에서 AF_UNIX 소켓 차단 | Gradle 이 `Unable to establish loopback connection` 으로 죽음 | 전용 임시 폴더를 만들어 `TMP`/`TEMP` 를 그쪽으로 돌림 |
| Android Studio 내장 JDK 가 Java 25 | Gradle 8.5 는 Java 21 까지만 지원 | JDK 17 을 따로 받아서 사용. 17~21 범위만 허용 |
| `NoDefaultCurrentDirectoryInExePath=1` | `gradlew.bat`, `java` 를 이름만으로 못 찾음 | 모든 실행 파일을 전체 경로로 호출 |
| `wmic` 제거됨 (Win11 최신) | APK 파일명 날짜가 비어버림 | PowerShell `Get-Date` 로 대체 |
| 배치 파일 인코딩 | 한글이 깨지고 명령이 잘림 | CP949 저장 + `chcp` 사용 금지 |

**AF_UNIX 차단은 Android Studio 에서도 똑같이 터진다.** Studio 에서 Gradle Sync 가
같은 오류로 실패하면, Studio 의 Gradle JVM 설정에 아래를 추가하면 된다.

```
-Djdk.net.unixdomain.tmpdir=C:/Users/<사용자>/.ezystocks-tools/tmp
```

> 배치 파일은 **CP949 로 저장되어 있고 `chcp` 를 쓰지 않는다.** 둘 다 의도된 것이다.
> 배치 파일 실행 도중 코드페이지를 바꾸면 cmd 가 파일을 읽던 위치를 잃어버려
> 명령이 앞부분씩 잘린 채 실행된다. 수정할 때 인코딩을 UTF-8 로 바꾸지 말 것.

### 빌드 확인 결과

```
유닛 테스트   126개 전부 통과 (컴파일 오류 0)
계측 테스트   13개 (Room 마이그레이션 + 구역 되돌리기. 실기기/에뮬레이터 필요)
디버그 APK    약 39MB
릴리스 APK    21MB (R8 난독화, 경고 0)
```

계측 테스트는 기기가 붙어 있어야 돈다.

```
.\gradlew.bat :app:connectedDebugAndroidTest
```

**스키마를 바꿨다면 이 테스트를 반드시 돌릴 것.** `runMigrationsAndValidate` 는 마이그레이션
실행 결과가 Room 이 기대하는 스키마와 정확히 같은지까지 확인한다. 손으로 쓴 `CREATE TABLE` 의
컬럼 순서·타입·인덱스가 하나만 어긋나도 여기서 걸린다. 이건 유닛 테스트로는 잡을 수 없고,
못 잡으면 사용자 기기에서 앱이 **시작하자마자 죽는다.**

`ZoneUndoTest` 도 같이 돈다. **되돌리기나 구역 수량 코드를 건드렸다면 반드시 돌릴 것.**
합계(`products.countedQty`)와 구역 합(`zone_counts.qty`)이 어긋나는 버그는 화면에 아무 표시도
남기지 않고, 실사가 다 끝난 뒤 리포트에서야 드러난다. 이 테스트가 그 등식을 고정한다.

R8 적용 후에도 Room 이 리플렉션으로 찾는 `AppDatabase_Impl` 이 DEX 에 이름 그대로 남아
있는 것을 확인했다. ProGuard 규칙을 건드릴 때 이 부분이 깨지지 않는지 반드시 확인할 것.

**요구 사항**: JDK 17 이상, Android SDK 34. 둘 다 Android Studio 를 설치하면 함께 깔린다.
minSdk 26 (Android 8.0) 이상에서 동작한다.

릴리스 서명을 하려면 프로젝트 루트에 `keystore.properties` 를 만든다(없으면 서명 없이 빌드된다).

```
storeFile=C:/keys/ezystocks.jks
storePassword=...
keyAlias=ezystocks
keyPassword=...
```

> 참고: `gradle/wrapper/gradle-wrapper.jar` 는 바이너리라 저장소에 넣지 못했다.
> `build-apk.bat` 이 최초 실행 때 자동으로 만들어 준다. Android Studio 에서 열어도 생성된다.

## 이 앱이 푸는 문제

브랜드마다 바코드에 품번·컬러·사이즈를 넣는 방식이 다르다. 특히 **사이즈 표기**가 제각각이다.

| 엑셀 표기 | 바코드 표기 | 해결 방식 |
|---|---|---|
| `M` | `00M`, `OOM` | 패딩 문자 제거 — 기계적으로 확정 (`SizeCode.canonical`) |
| `XL` | `0XL`, `OXL`, `2XL` | 패딩 제거 + 배수 표기 전개 — 기계적으로 확정 |
| `M` | `095` | **의미 매핑. 유도 불가** → 아래 3단계로 해결 |

### 실제 브랜드 파일 분석 결과

작업 중에 실제 재고 파일 두 개를 전수 검증했다. 여기서 나온 사실이 설계를 바꿨다.

**피엘라벤** (`피엘라벤_nogroup.xlsx`, 2,576행)

```
바코드 = 품번 + 컬러 + 사이즈     2,576 / 2,576 = 100% 일치
품번 11자(2,533) 또는 12자(43)    ← 길이가 다르다
컬러  2자(2,450) 또는 3자(126)    ← 길이가 다르다
사이즈 4.5 / 5.5 / 6.5 ...        ← 소수점이 들어간다

  W265WSO05SO + AB7 + 5.5  =  W265WSO05SOAB75.5
  W265WSO05SO + HX  + 4.5  =  W265WSO05SOHX4.5
```

- 고정 자릿수로는 둘 중 하나만 맞출 수 있다 → **카탈로그 대조 방식**([`CatalogSegmenter`](app/src/main/java/com/ezystocks/inventory/domain/barcode/CatalogSegmenter.kt))을 추가했다.
  자릿수를 고정하지 않고 재고 목록의 품번/컬러와 대조해 경계를 찾는다.
- 소수점을 지우면 `4.5 → 45` 가 되어 `4, 5, 6, 45, 55, 65` 순으로 정렬된다 → 소수점을 보존하도록 고쳤다.
- 바코드 열이 100% 채워져 있으므로 **실물을 한 개도 찍지 않고** 임포트 직후 구조 학습이 끝난다.

**머렐** (`머렐.xlsx`, 4,371행, 840품번)

```
헤더가 2행       1행에 열 이름, 2행에 "수량"만, 데이터는 3행부터
바코드 열 없음   → 실물 샘플로 구조를 잡아야 한다
사이즈가 다양    220~290(mm), 70~115(호수), S/M, M/L, L/XL, FREE, WS/WM/WL
수량 열이 3개    재고 / 현재고 / 가용재고
```

- `M/L` 과 `ML` 이 **둘 다 존재**한다 → 슬래시를 지우면 서로 다른 사이즈가 하나로 뭉개진다. 보존하도록 고쳤다.
- `S/M` 은 `S` 와 `M` 사이에 정렬되어야 한다 → 조합 사이즈 정렬 규칙을 넣었다.
- 열 자동 인식이 `실사`가 아닌 `현재고`를 고르는지, `스타일코드`/`스타일명`을 구분하는지 테스트로 고정했다.

> `피엘라벤_품번별.xlsx` 는 품번 단위 요약이라 컬러/사이즈/바코드가 비어 있다.
> 실사에는 `_nogroup` 쪽(단품 단위)을 써야 한다.

### `095 = M` 을 알아내는 3단계

1. **엑셀에 바코드 열이 있으면 전체 행으로 자동 학습**
   `(바코드, 품번, 컬러, 사이즈)` 정답 쌍이 수백~수천 건 있으므로 구조와 표기 대응을
   확신을 갖고 뽑아낸다. 사용자는 실물을 **한 개도 찍지 않아도 된다.**
   → `BarcodeLayoutLearner.learnFromMaster`

2. **바코드 열이 없으면 샘플 2~3개로 구조만 추정**
   구조(어디가 품번/컬러/사이즈인지)는 알 수 있지만 `095 = M` 은 유도할 수 없다.
   억지로 추측하지 않고 넘어간다.
   → `BarcodeLayoutLearner.learnFromSamples`

3. **조사 중 처음 마주쳤을 때 한 번만 묻고 영구 학습**
   품번·컬러까지 확인된 상태이므로 "이 바코드의 `095` 는 어떤 사이즈인가요?" 만 묻는다.
   한국 호수 대응표(`SizeChart`)로 `M` 을 미리 추천해 두므로 대부분 한 번 탭으로 끝난다.
   답은 `sku_aliases` 테이블에 저장되어 **이후 모든 스캔이 자동 처리**된다.
   같은 브랜드로 다시 조사하면 그 설정을 그대로 물려받는다.

## 스캔 해석 순서

뒤로 갈수록 사용자 개입이 늘어난다. 되도록 앞에서 끝내는 것이 설계 목표다.

| 단계 | 조건 | 동작 |
|---|---|---|
| 1 | 학습된 개별 바코드 매핑 | 즉시 +1 |
| 2 | 엑셀 바코드 열과 일치 | 즉시 +1 |
| 3 | 학습된 구조로 분해 + 표기 변환표로 SKU 특정 | 즉시 +1 |
| 4 | 구조가 없거나 빗나가도 **마스터 대조**로 재시도 | 즉시 +1 |
| 5 | 품번·컬러까지 확인, 사이즈만 모름 | **사이즈만** 질문 → 영구 학습 |
| 6 | 품번·사이즈까지 확인, 컬러만 모름 | **컬러만** 질문 → 영구 학습 |
| 7 | 품번만 확인 | 매트릭스에서 칸 선택 |
| 8 | 전부 실패 | 유사 품번 추천 + 직접 검색 |

4단계는 구조 학습을 건너뛴 세션이나 규칙에서 벗어난 예외 바코드를 건지는 안전망이다.
품번 집합은 세션 캐시(해시)에 올라가 있으므로 **대조 자체가 쓰는 DB 질의는 품번 인덱스 1회**뿐이다.

스캔 한 건 전체로 보면 해석에 3~6회, 수량 기록과 매트릭스 갱신까지 더해 열 번 안팎이 나간다.
전부 인덱스 조회이고 기록은 한 트랜잭션으로 묶여 있어 스캐너 연사 속도를 따라간다.
전 행을 메모리로 올리는 경로(`buildMasterIndex`, `allProducts`)는 스캔 경로에서 부르지 않는다.

`ScanResult` / `InventoryRepository.processScan` 참고.

## 구역별 실사

한 조사 안에서 **창고A → 매장 → 창고B** 처럼 장소를 나눠 센다. 스캔은 항상 "지금 선택된 구역"에
기록되고, 실사 화면 하단과 홈의 진행 중 카드에서 구역을 눌러 전환한다.

세션을 구역마다 따로 만들지 않는 이유는 **전산재고가 매장 전체 기준**이기 때문이다.
구역별로 세션을 쪼개면 과부족 비교가 전부 무의미해진다.

```
products.countedQty   전 구역 합계.  전산재고 비교·진행률·정합률·리포트가 전부 이 값을 본다
zone_counts.qty       구역별 수량.   매트릭스 칸의 우상단 배지, 수량 팝업의 편집 대상
```

합계 컬럼을 그대로 둔 것이 핵심이다. 집계 경로를 하나도 건드리지 않아도 구역 기능이 붙는다.

- 매트릭스 칸은 **두 숫자**를 보여준다. 큰 숫자가 전 구역 합계(전산과 비교되는 값),
  우상단 배지가 이 구역에서 센 수량.
- **수량 팝업이 고치는 것은 이 구역 수량**이다. 합계는 그 차이만큼만 따라 움직인다.
- **되돌리기와 최근 작업도 이 구역 것만** 본다. 세션 전체에서 고르면 창고B 에서 되돌리기를
  눌렀는데 창고A 것이 취소된다.
- **구역 이름을 앱이 지어주지 않는다.** 자동으로 "기본 구역" 같은 이름이 붙으면 서로 다른
  장소에서 센 물건이 같은 이름 아래 섞여도 아무도 알아채지 못한다. 구역이 없으면 화면이 묻는다.

## 입력 수단 (4가지)

- **카메라** — ML Kit 번들 모델. Google Play 서비스 없이 오프라인 동작.
  미리보기는 조준칸 높이만 남겼다. 주변 풍경은 조준에 도움이 안 되고 매트릭스 자리만 먹는다
- **산업용 PDA** — Zebra DataWedge / Point Mobile / Honeywell / Bluebird 브로드캐스트
- **바코드 리더기(HID)** — USB-C OTG / 블루투스. 키 입력 속도로 사람 타이핑과 구분
- **수동** — 품번·품명·바코드 검색, 매트릭스 칸 길게 눌러 수량 팝업.
  키보드는 **앱 안에 직접 그린다**(아래 참고)

### 리더기를 꽂으면 키보드가 안 뜬다 → 앱 안에 키보드를 넣었다

리더기를 USB/블루투스로 붙이면 안드로이드는 그것을 **물리 키보드**로 본다.
물리 키보드가 붙어 있으면 시스템은 화면 키보드를 아예 띄우지 않는다.
그래서 **리더기를 꽂은 채로는 품번을 손으로 칠 방법이 없었다.**

시스템 설정(`설정 > 시스템 > 언어 및 입력 > 물리적 키보드 > 화면 키보드 표시`)을 켜면 풀리지만,
매장 폰마다 들어가서 켜 줄 수는 없다. 그래서 우리 화면 위에 우리가 그린다.

| | |
|---|---|
| 배열 | **천지인**(한글) / 쿼티(영문) / 숫자+기호 |
| 기본값 | 켜짐 (`설정 > 키보드` 에서 끌 수 있다) |
| 붙는 곳 | 품번 검색, 바코드 직접 입력, 구역 이름 입력 |

부수 효과가 두 가지 더 있다.

1. **한글 입력기 문제가 같이 사라진다.** 내장 키보드는 `KeyEvent` 를 만들지 않으므로
   리더기 가로채기(`HidBarcodeHandler`)와 서로 간섭하지 않는다. **리더기를 켜 둔 채로
   손으로도 칠 수 있다.** 예전에는 "손으로 입력"을 켜면 리더기를 꺼야 했다.
2. **구역 이름 다이얼로그의 막다른 길이 없어졌다.** 구역이 하나도 없으면 그 다이얼로그는
   닫을 수 없는데, 리더기를 꽂은 상태에서는 거기서 아무것도 칠 수 없어 조사를 시작할 방법이
   없었다. 이제 그 다이얼로그도 키보드를 함께 띄운다.

영문만 쿼티인 이유는 품번 때문이다. `MM24-JK01` 을 멀티탭(ABC 두 번 눌러 B)으로 치면
품번 하나에 스무 번을 눌러야 한다. 한글은 품명 검색용이라 천지인으로 충분하다.

조합 규칙은 `CheonjiinEngine` 이 갖고 있고 안드로이드 타입을 전혀 쓰지 않는다.
순수 로직이라 유닛 테스트로 고정했다(20개). 특히 "받침이 다음 글자로 넘어가는" 규칙
(`한` + `ㅏ` = `하나`)은 틀려도 눈에 잘 안 띄는데, 틀리면 품명 검색이 통째로 안 먹는다.

### 리더기가 안 먹을 때 (실제로 겪은 것들)

바코드 리더기(B-210)를 붙이면서 세 단계를 거쳤다. 증상이 비슷해 보여도 원인이 전부 다르다.

| 증상 | 원인 | 대응 |
|---|---|---|
| 삑 소리는 나는데 아무것도 안 들어옴 | 리더기가 USB **키보드(HID)** 모드가 아님 | 설명서 2.1 Interface Selection 에서 `<<USB__>>` 선택. `USB_COM`/`RS-232`/PS2 `Keyboard` 는 안드로이드가 못 받는다 |
| 앱에서만 안 들어옴 | "바코드" 모드가 가로채기를 **끄고** 입력칸 포커스에 의존했는데 그 포커스 요청이 조용히 실패 | 포커스와 무관하게 액티비티 레벨에서 받도록 변경 |
| **숫자만** 들어오고 영문이 사라짐 | 한글 입력기가 IME 단계에서 자음/모음 키를 **조합 대상으로 먼저 소비** | `dispatchKeyEventPreIme` 로 IME 앞단에서 가로채고, `keyCode` 로 읽음 |

마지막 것이 가장 중요하다. 두 가지를 같이 해야 한다.

1. **IME 보다 먼저 받는다.** 키 전달 순서가
   `dispatchKeyEventPreIme -> [IME] -> ... -> Activity.dispatchKeyEvent`
   인데, 한글 입력기가 가운데에서 영문 키를 먹어버려 Activity 까지는 숫자만 내려온다.
   `MainActivity` 의 `PreImeKeyInterceptor` 가 그 앞에서 가져간다.
2. **`unicodeChar` 를 믿지 않는다.** 그건 "현재 입력기 기준 이 키가 무슨 글자인가"라
   한글 입력기가 켜져 있으면 `M` 자리 키가 `ㅡ` 로 온다. `keyCode` 는 배열·입력기와 무관한
   물리 키 식별자다. `ScannerKeyMap` 이 표로 변환하고, 표에 없는 키는 **출력 가능한 ASCII 일 때만**
   받아들여 한글이 어떤 경로로도 바코드에 섞이지 않게 한다.

가로채기는 바코드 문자를 **소비**한다. 그래서 `HidBarcodeHandler.enabled` 는 **기본이 꺼짐**이고
리더기 값을 받을 화면이 떠 있는 동안에만 켠다. 켜 둔 채로 다른 화면에 가면 물리 키 입력이
통째로 사라진다.

> 예전에는 여기에 더해 "손으로 입력"을 켤 때도 가로채기를 껐다. 지금은 **끄지 않는다.**
> 내장 키보드가 `KeyEvent` 를 만들지 않기 때문에 둘이 부딪힐 일이 없다.
> 기기 키보드를 쓰겠다고 명시적으로 고른 경우에만 끈다.

> 참고: 리더기의 `ALT Mode`(설명서 2.2.2) 는 윈도우에서 한글 상태 문제를 푸는 표준 해법이지만
> **안드로이드에서는 켜지 말 것.** 안드로이드에는 Alt 코드 입력이 없어서 폰 쪽이 깨진다.

## 화면

### 왜 밝은 테마인가

취향이 아니라 조명이다. 매장과 창고는 형광등이 정면으로 들어오는 곳이라 **어두운 화면은
그대로 거울이 된다.** 밝은 배경은 주변광이 셀수록 오히려 잘 보이고, 폰을 최대 밝기로
켜 둘 필요도 없어서 몇 시간짜리 작업에서 배터리가 덜 닳는다.

색을 고른 원칙은 `ui/theme/Theme.kt` 에 적어 두었다. 요약하면

- 배경은 순백이 아니라 아주 옅은 청회색(`#F3F5F9`). 순백은 형광등 아래에서 눈이 부시고
  흰 카드를 얹었을 때 카드 경계가 사라진다
- 본문 글자는 `#0F172A`. 순검정은 밝은 배경에서 대비가 지나쳐 잔상이 남는다
- 상태색은 전부 **글자용(진한 색)과 칸 배경용(연한 색) 두 짝**으로 둔다

### 매트릭스 칸 색

```
맞음    연한 초록   =  "맞음"
부족    연한 붉은색 ▼  "3개 부족"
남음    연한 파란색 ▲  "1개 남음"
미실사  연한 회색   ·  "안 셈"
```

칸 배경색이 곧 상태다. 글자를 읽기 전에 **어디가 문제인지부터** 눈에 들어와야 한다.
다만 색만으로 구분하지는 않는다. 기호와 말을 항상 함께 적어서 색약에서도 읽히게 한다.

### 숫자를 말로 바꿨다

예전에는 `2 / 1 / -1` 처럼 세 숫자를 슬래시로 붙여 놓았다. 두 가지가 문제였다.

1. 어느 것이 전산이고 어느 것이 실사인지 **매번 다시 생각해야 한다**
2. `-1` 은 부호를 한 번 더 해석해야 뜻이 나온다. 매대 앞에서 그 한 박자가 오독이 된다

그래서 숫자 위에 이름표를 붙이고, 과부족은 부호가 아니라 **말**로 쓴다.

```
┌──────┬──────┬──────────┐
│ 전산  │ 실사  │   차이    │
│  2   │  1   │ ▼ 1개 부족 │
└──────┴──────┴──────────┘
```

이 표기는 `ui/component/StockIndicators.kt` 한 곳에만 있다(`QtyTripleRow`, `StatusPill`).
매트릭스·홈·리포트·다이얼로그가 전부 같은 부품을 쓰므로 규칙이 한 곳에서만 바뀐다.
화면마다 표기가 다르면 "이 숫자가 아까 그 숫자인가"를 매번 따져야 한다.

### 가로 모드 — 폭과 높이를 따로 본다

세로 화면은 입력 패널과 매트릭스가 세로 공간을 나눠 쓴다. 가로로 눕히면 그 방식이 최악이 된다.
남는 것은 가로 폭인데 둘 다 세로로 쌓여 있어서 매트릭스에 두세 줄밖에 안 남고,
좌우로는 빈 공간이 넓게 뜬다. 그래서 가로에서는 입력 패널을 왼쪽 기둥으로 세운다.

**여기까지는 예전에도 그랬다. 문제는 그 판단을 불리언 하나로 했다는 것이다.**

`wide` 하나가 서로 다른 두 가지를 동시에 정하고 있었다.

- 입력 패널을 옆으로 세울까 → **폭**의 문제
- 칸과 글자를 키우고 크롬을 얼마나 둘까 → **높이**의 문제

태블릿에서는 둘이 같이 참이라 드러나지 않았다. **가로로 누운 스마트폰에서 갈라진다.**
폭은 태블릿만큼 넓은데 높이는 세로 폰의 절반도 안 된다. Pixel 5 를 눕히면 상단바·입력방식
줄·구역 바·통계 바를 빼고 본문에 175dp 쯤 남는데, 거기에 태블릿용 상수가 그대로 적용됐다.

| 상수 | 값 | 남은 높이 175dp 에서 벌어진 일 |
|---|---|---|
| `GRID_CHROME_HEIGHT` | 272dp | `175 - 272` 이 음수 → 하한 240dp 로 튕김. 실제 공간보다 큰 값이 배정돼 행과 범례가 잘림 |
| `GridDensity.WIDE` 칸 높이 | 110dp | 머리말(110dp) + 사이즈 헤더(48dp) 만으로 자리가 참 |
| 내장 키보드 | 238dp | 기둥 전체보다 키보드가 큼 → 검색칸이 0으로 찌그러짐 |
| 카메라 패널 하한 | 180dp | 본문 높이를 이미 넘음 |

결과는 **매트릭스 행이 한 줄도 안 보이고**, 검색 모드에서는 **입력칸이 통째로 사라져**
무엇을 치고 있는지 볼 수 없는 화면이었다. 태블릿에서는 멀쩡했다.

그래서 두 축을 분리했다(`ui/layout/ScreenShape.kt`).

```
twoPane = 창 폭   >= 600dp    입력 패널을 옆 기둥으로 세울 수 있는가
short   = 창 높이 <  500dp    세로가 귀한 화면인가 (가로로 누운 폰)
```

기준을 **창 크기**로 잡는다. 본문(Scaffold 안쪽) 크기로 잡으면 순환이 된다. 크롬 높이가
모양에 따라 달라지는데 그 크롬을 뺀 값으로 다시 모양을 정하는 셈이기 때문이다.
가로 폰은 높이가 430dp 를 넘지 않고 가장 작은 태블릿도 뉘었을 때 570dp 는 나온다. 그 사이를 가른다.

| 화면 | 세로 폰 | **가로 폰** (`twoPane && short`) | 태블릿 (`twoPane && !short`) |
|---|---|---|---|
| 실사 배치 | 위아래 | 좌우 | 좌우 |
| 매트릭스 칸 | 100 x 96 | **96 x 68** (`SHORT`) | 126 x 110 (`WIDE`) |
| 품번 머리말 | 쌓기 | **한 줄로 눕힘** | 쌓기 |
| 범례 | 표시 | **접음** (34dp = 행 반 줄) | 표시 |
| 입력 방식 줄 | 상단바 아래 | **기둥 머리로** | 기둥 머리로 |
| 구역 바 + 통계 바 | 두 줄 (117dp) | **한 줄** (52dp) | 두 줄 |
| 내장 키보드 | 화면 바닥 | **입력칸 옆** | 기둥 바닥 |
| 홈 요약 카드 | 쌓기 (150dp) | **한 줄** (40dp) | 쌓기 |
| 리포트 요약·검색·필터 | 세 줄 | **두 줄** | 세 줄 |

**격자 높이는 이제 계산하지 않는다.** `GRID_CHROME_HEIGHT` 같은 손으로 적은 값은 실제
크롬과 어긋나는 순간 행을 자르거나 빈 칸을 남긴다. 행 영역에 `weight(1f, fill = false)` 를
주면 머리말·헤더·범례를 재고 **남는 만큼**을 쓰되 내용보다 커지지는 않는다.
적어 둔 값이 없으므로 어긋날 것도 없다.

**키보드를 옆에 세운 이유**도 같은 종류다. 아래에 두면 기둥 높이(약 340dp)를 입력칸 90dp 와
키보드 180dp 가 나눠 갖고 결과 목록에 한 줄이 반쯤 남는다. 품번을 찾는 화면에서 결과가
한 줄이면 찾는 일이 안 된다. 옆에 세우면 둘이 높이를 다투지 않는다.
**모자란 것은 세로지 가로가 아니다.**

입력칸은 키보드와 함께 스크롤 **밖**에 고정한다. 한 덩어리로 묶어 스크롤 영역에 넣었더니
그 영역이 0으로 찌그러졌을 때 입력칸이 같이 사라졌다. 줄어들어도 되는 것은 결과 목록뿐이다.

다이얼로그도 같이 고쳤다. 목록 높이가 280dp 로 박혀 있어서 가로 폰(창 높이 460dp)에서
제목·목록·버튼의 합이 화면을 넘어 **확인 버튼을 누를 수 없었다.** 이제 창 높이에 비례한다.
폭에는 상한(620dp)을 둔다 — `widthIn` 을 `fillMaxWidth` **앞**에 놓아야 먹는다.

회전은 `AndroidManifest` 의 `configChanges` 로 처리하므로 화면이 다시 만들어지지 않는다.
**실사 도중에 폰을 돌려도 조사 상태가 그대로다.**

### Apache POI 를 쓰지 않은 이유

1. Android 에는 `javax.xml.stream`(StAX) 이 없어 `poi-ooxml` 이 실기기에서
   `NoClassDefFoundError` 로 죽는다. 에뮬레이터에서는 통과하는 경우도 있어 더 위험하다.
2. APK 가 15MB 이상 늘고 ProGuard 설정이 복잡해진다.
3. 필요한 건 "시트 읽기 / 시트 쓰기"뿐이고, xlsx 는 XML 이 든 zip 이다.
   안드로이드 기본 `ZipFile` + `XmlPullParser` 로 충분하다.

**제약**: 구형 `.xls`(BIFF) 는 지원하지 않는다. 앱이 감지해서 안내 메시지를 띄운다.

## 데이터 안전장치

- **세션 이어하기** — 홈 화면에서 진행 중인 조사를 언제든 재개
- **전체 이력 기록** — 스캔·수동 수정·반자동 매칭이 모두 `scan_logs` 에 남는다.
  `prevQty` 를 저장하므로 어떤 작업이든 정확히 되돌릴 수 있고, 연속 되돌리기도 가능
- **되돌리기는 델타만 되돌린다** — `+1` 을 취소하면 **그 1개만** 빠진다. 그 사이 다른 구역이
  같은 상품을 셌어도 그 수량은 건드리지 않는다.
  `SET`(수량 직접 지정)은 "이 값으로 덮어썼다"는 기록이라 뒤에 다른 작업이 있으면
  단독 취소가 불가능하다. 그 경우는 조용히 실패하지 않고 **이유를 띄워 거절**한다
  (`RevertResult.Refused`). 현장에서 "눌렀는데 아무 일도 안 일어남"이 가장 나쁜 응답이다
- **파괴적 마이그레이션 금지** — `fallbackToDestructiveMigration()` 을 쓰지 않는다.
  스키마 변경 시 `AppDatabase` 에 마이그레이션을 추가할 것. 스키마는 `app/schemas/` 에 남는다
- **클라우드 백업 제외** — 매장 재고는 기밀이므로 `data_extraction_rules.xml` 에서 제외.
  반출은 명시적인 "엑셀 내보내기 + 공유" 경로만 사용
- **중복 행 합산** — 같은 규격이 여러 행에 있으면 덮어쓰지 않고 더한다. 몇 행을 합쳤는지 보고
- **CSV 인코딩 자동 판별** — CP949(EUC-KR) 로 저장된 한국 ERP CSV 도 한글이 깨지지 않는다

## 고친 것 (2026-09-13)

| 무엇 | 증상 |
|---|---|
| **되돌리기가 구역 수량을 합계보다 더 내렸다** | 되돌리기는 합계를 0 아래로 내리지 않는데(`coerceAtLeast(0)`) 구역 수량에는 `log.delta` 를 그대로 뺐다. 합계가 0에서 멈춘 만큼 **구역만 더 내려가** 둘이 갈라진다. 창고A +1 → 수량 팝업에서 0으로 지정 → 그 +1 을 취소 하면 합계 0 / 구역 -1 이 된다. 화면에는 아무 표시도 안 남는다. 이제 의도한 폭이 아니라 합계가 **실제로 움직인 폭**을 구역에도 그대로 쓴다. `setQuantity` 도 같은 방식으로 폭을 먼저 깎는다. `ZoneUndoTest` 가 고정한다 |
| 검색이 매 글자마다 전체 행을 훑었다 | `itemKey LIKE '%키%'` 는 선행 와일드카드라 인덱스를 못 탄다. 게다가 SQLite 의 LIKE 는 기본이 대소문자 무시라 `LIKE '키%'` 로 바꿔도 BINARY 인덱스를 못 쓴다. 품번 접두 검색을 `itemKey >= :key AND itemKey < :keyEnd` 범위 비교로 바꿔 `(sessionId, itemKey)` 인덱스를 타게 하고, 그것으로 화면을 못 채웠을 때만 기존 중간 일치 검색을 얹는다. 실제 파일(4,371행)에서는 티가 안 나지만 `MAX_ROWS` 는 20만이고 검색은 타이핑 중 180ms 마다 도는 자리다 |
| README 의 DB 질의 횟수가 실제와 달랐다 | "스캔 1건당 DB 질의는 최대 1회" 는 `catalogTokens` 한 함수에만 맞는 말이었다. 스캔 한 건 전체로는 해석 3~6회 + 기록·매트릭스 갱신까지 열 번 안팎이 나간다. 범위를 정확히 적고 실제 비용을 `processScan` 주석에 남겼다 |

## 고친 것 (2026-09-12)

| 무엇 | 증상 |
|---|---|
| **구역별 되돌리기가 다른 구역 수량을 지웠다** | `undoLast` 가 합계를 `prevQty`(그 시점의 **전 구역 합계** 스냅샷)로 복원했다. 창고A +1 → 매장 +1 → 창고A 되돌리기 를 하면 합계가 0으로 떨어져, 매장에서 센 1개가 사라졌다. 화면에는 아무 표시도 안 남고 리포트에서야 드러난다. 이제 `revertLog` 와 같은 규칙(델타의 역)으로 되돌린다. `ZoneUndoTest` 가 고정한다 |

| 리더기를 꽂으면 아무것도 칠 수 없었다 | 위 "리더기를 꽂으면 키보드가 안 뜬다" 참고 |

## 알려진 제약 / 남은 일

- UI 문자열이 한국어로 하드코딩되어 있다. 다국어가 필요해지면 `strings.xml` 로 추출해야 한다
  (여기서 말하는 "범용성"은 브랜드·엑셀 양식 범용성에 집중했다)
- `.xls` 미지원 (위 참고)
- 계측 테스트는 마이그레이션 3개 + 구역 되돌리기 5개뿐이다.
  DAO 쿼리와 스캔 파이프라인(`processScan` 8단계)의 기기 테스트가 있으면 좋다
- **구역 삭제가 없다.** 이름 변경(칩 길게 누르기)만 된다. 오타로 만든 구역을 지울 수 없다
- 리포트는 전 구역 **합계**만 내보낸다. 구역별 내역 시트는 없다
- 내장 키보드에 **커서 이동이 없다.** 항상 끝에 붙고 끝에서 지운다. 품번·품명 검색에는
  충분하지만 긴 글을 고치기에는 부족하다
- 내장 키보드에서 **같은 자음을 연달아 두 번** 치려면(예: `ㄱㄱ`) 사이에 다른 키가 필요하다.
  천지인은 같은 키 연타를 순환(`ㄱ→ㅋ→ㄲ`)으로 쓰기 때문이다
- `local.properties` 의 `sdk.dir` 는 `build-apk.bat` 이 실행할 때마다 덮어쓴다.
  **Android Studio 로 직접 열면** 그 값이 이 PC 와 안 맞을 수 있으니 한 번 확인할 것
- `output/` 에 빌드한 APK 가 계속 쌓인다. 주기적으로 비울 것
- 이전 버전 소스는 `_backup_20260911/` 에 남겨두었다. 확인 후 지워도 된다
